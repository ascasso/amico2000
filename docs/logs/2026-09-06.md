# Engineering Log — 2026-09-06

## Front-End Recreation of the ASEL Board

### Summary

Reworked `index.html` so the emulator's interface recreates the appearance of
the real AMICO 2000 board rather than presenting a generic dark panel with a
separate display box and keypad box. Purpose: this is a memorial project, and
the project owner asked for an interface that conveys the experience of using
the original hardware, not only its behavior.

Reference material was the set of board photographs and the PCB layout render
archived from ComputerHistory.it. The layout images are only 600px wide, so the
result is a reconstruction driven by those photographs rather than a
pixel-accurate reproduction.

What the page now renders as a single green PCB slab:

- Solder-mask green board with a copper routing layer, gold vias, plated
  mounting holes, a bus edge connector, and a `J1 EXP` expansion header.
- Power section: transformer, two electrolytic capacitors, and a 7805 with
  heatsink.
- Logic: 6502, 8255 (corrected below), 2716 monitor ROM, two 2114 RAMs, 74-series glue, a crystal
  can, and discrete resistors and ceramic capacitors.
- Five red indicator LEDs, two of which remain the existing `led-power` and
  `led-run` elements driven by `main.js`.
- The seven-segment display block, and the keypad in the arrangement printed on
  the real board:

```text
[NOR|SS] [RUN] [ ↑ ] [DA]        0 1 2 3
[ RES  ] [HLT] [REG] [AD]        4 5 6 7
                                 8 9 A B
                                 C D E F
```

Red keycaps for the hex digits and blue for the function keys, each sitting
inside its printed silkscreen legend box the way the original does, with the
keycap itself blank. `A.S.E.L. AMICO 2000` is silkscreened vertically at the
bottom-right edge.

The board interior is sized in container query units (`cqw`) so the whole
assembly scales as one object; below 760px the board pans horizontally instead
of reflowing, since a board is a fixed-proportion physical thing. The run/step/
reset controls, the register readout, and the shortcut reference moved off the
board into plain panels underneath.

### Scope and Compatibility

No emulator behavior was changed. The rework deliberately preserved the entire
DOM contract that `main.js` and `display.js` depend on:

- All fourteen element IDs (`btn-run`, `btn-step`, `btn-reset`, `btn-load`,
  `led-power`, `led-run`, `reg-pc`, `reg-a`, `reg-x`, `reg-y`, `reg-sp`,
  `reg-flags`, `rom-file`, `display`).
- The `.key` class and all 23 `data-key` values, unchanged.

Two presentational changes did land outside `index.html`:

- The `GO` and `PC` keys are now labelled `RUN` and `HLT` after the legends on
  the real board. Their `data-key` values still read `go` and `pc`, and the
  matrix positions in `amico2000.js` are untouched. The `HLT`/`pc`
  correspondence is inferred from position on the board and is **not** confirmed
  against the monitor ROM; this is worth revisiting alongside the existing
  keyboard-matrix cleanup, since `keyMap` currently has only three distinct
  function-key positions (`[2,1]`, `[2,2]`, `[2,3]`) for seven physical keys.
- `main.js` lost the `▶`/`⏸` glyph prefixes on the run/stop button label, to
  match the plain-text control panel. Four characters, label text only.

Two implementation details worth recording, because both were latent traps:

- `main.js` sets `button.style.transform = 'translateY(3px)'` on key press,
  which replaces any transform used for layout. The keycaps are therefore
  centered with `left`, not `translateX(-50%)`, or they would jump sideways when
  pressed.
- The pressed state is carried by `box-shadow` and `filter` rather than a
  transform, for the same reason.

## ROM Write Protection (#31)

### Problem

`CPU6502.write()` dispatched registered I/O callbacks and then wrote straight
into its flat 64KB array. The machine layer registered PIA callbacks but
nothing for the PROM regions, so a guest `STA $FE00` patched the monitor.
`Amico2000.reset()` clears RAM and resets the CPU but has no pristine ROM to
restore, so the damage survived Reset.

Reproduced in Node against the current sources: after `LDA #$00 / STA $FE00`,
byte `$FE00` read `$00` instead of `$85`, and still read `$00` after
`machine.reset()`.

The escalation that decides the severity is the vector table. `$FFFA-$FFFF`
sits inside the monitor region, and `CPU6502.reset()` takes its new PC from
`$FFFC`. A guest `STA $FFFC / STA $FFFD` therefore left reset landing at
`$0000`: the board could not be recovered by any reset path, the toolbar Reset
control included. Confirmed in the same run, PC = `$0000` after reset.

Auditing the other paths that reach memory found two further bypasses, both
also reproduced:

- `loadProgram(data, address)` calls `cpu.loadBinary()` directly, so a `.bin`
  loaded at a PROM address overwrote it.
- The trapped IC10 tape LOAD takes its destination from guest RAM
  (`$0001/$0002`) or from the tape record, and only checked that the span fit
  inside the 64KB array. A LOAD with override `$FE00` wrote program bytes over
  the monitor.

### Approach

Protection lives in the machine's address decoding, not in the CPU core. The
PROMs at IC9 and IC10 have no write line, so a store into their space is
decoded, driven onto the bus, and lost. `Amico2000._protectROM()` models that
by registering write callbacks over both regions, exactly the mechanism the
PIA already uses; `cpu6502.js` is unchanged and keeps its generic writable flat
memory. `Amico2000.ROM_REGIONS` is the one place the layout is declared.

The IC10 region is protected whether or not a cassette PROM has been loaded.
An empty socket latches a store no better than a fitted chip does, so both
configurations behave the same and there is no state-dependent rule to explain.

ROM is modelled as immutable rather than as restored-on-reset. Nothing keeps a
pristine copy, and nothing needs to: reset on the real machine does not reload
the PROMs either, because they cannot be written in the first place.

The three direct-memory paths were handled by intent rather than uniformly.
`loadMonitorROM()` and `loadCassetteROM()` are the emulator's equivalent of
fitting a chip, so they keep writing `cpu.memory[]` and are merely bounded to
the size of their socket, which also stops an oversized or wrongly identified
image from wrapping past `$FFFF` into zero page. `loadProgram()` throws, since
its caller in `main.js` already surfaces the message in an alert. The tape LOAD
returns the IC10 error convention (`$0000 = $FF`) instead of throwing, because
it runs inside a trapped ROM entry point where the monitor expects a status
byte.

`amico.writeMemory()` goes through `cpu.write()` and so can no longer patch ROM
from the console. That is intentional and consistent with the hardware; the ROM
loaders remain the supported way to change a PROM image.

### Scope

Left alone deliberately: `$0800-$FAFF` is unmapped on a 2KB machine but stays
writable, because the memory map documents RAM as expandable and narrowing that
is a separate fidelity question. Issue #35 (the embedded `CASSETTE_ROM` array
is not a valid `prom.ic10` dump) is untouched; this change defines how the
region behaves, not what belongs in it.

## RES Drives the Reset Line (#30)

### Problem

Escape was mapped to key matrix position `[2, 1]`, Backspace to `[0, 5]`, and
the on-screen RES button delegated to Escape. All three only set a bit in the
scanned matrix, so RES depended entirely on the running program getting round
to reading the keyboard. Reproduced in Node: a CPU spinning in `JMP $0200`
ignored all three, and a CPU halted on `$FF` stayed halted.

Both aliases also sat on positions shared with other keys. `[2, 1]` is AD/REG
and `[0, 5]` is hex 5, so pressing RES also typed something.

A third defect surfaced while writing the coverage: `keyDown()` referenced a
bare `window.debugKeyboard`, which throws a `ReferenceError` under Node. The
keyboard path could not be tested at all without fixing it.

### What the hardware does

The Sperimentare supplement settles the semantics. Its key reference describes
RES as "Reset = Azzeramento. Permette l'inizializzazione del sistema
all'accensione, visualizza la locazione di memoria 0000, permette di arrestare
l'esecuzione di un programma utente in qualsiasi momento passando il controllo
del sistema al monitor" (page 44 of the extraction, line 2013). Stopping a user
program *at any moment* is only possible from the processor's reset line, not
from a scanned key.

The same source settles the RAM question, which the issue asked to decide
explicitly rather than by default. The clock tutorial (lines 2884-2896) has the
reader press RES to stop the program running at `$0300`, then re-enter values
at `$0000-$0002` and adjust `$0312` to trim the clock rate. The program is
still in memory after RES. Clearing RAM on RES would make the documented
workflow impossible.

### Approach

Two resets, kept apart and both documented:

- `res()` is the RES key. It clears the key matrix, unhalts the CPU, calls
  `cpu.reset()` so the CPU vectors through `$FFFC` to `$FE22`, and clears the
  PIA and display because the 8255's RESET pin is on the same line. RAM is
  untouched.
- `reset()` is the power-on reset, with exactly the behavior it always had:
  clear 2KB of RAM, seed `$03FC-$03FF` to `$FE30`, then call `res()`.

`Escape` and `Backspace` left `keyMap`/`altKeyMap` for a `resetKeys` set that
`keyDown()` checks first, which is what makes RES independent of ROM keyboard
scanning and simultaneously removes the phantom AD and 5 input. `keyUp()`
returns early for them, and `res()` clears the whole matrix, so no alias can
leave a cell stuck down. `pressKey('res')` funnels through the same `keyDown()`
path and skips the auto-release timer, since a reset line has nothing to
release.

Two consequences of preserving RAM are recorded rather than worked around,
because both match the hardware. The monitor's RAM-resident IRQ/NMI vectors at
`$03FC-$03FF` survive RES, since `$FE22` reinitialises `$FA`, `$FB` and `$FE`
but not those; the power-on reset is the way back from a program that trashed
them. And RES does not touch `this.running`: pausing is a debugging facility
with no counterpart on the board, so a paused machine stays paused and can be
stepped from `$FE22`.

### UI

Two controls named "Reset" doing different things was the confusion the issue
reported, so the bench control is now labelled **Cold reset** with a tooltip
saying it clears RAM, the RES keycap tooltip says it keeps RAM, and the
shortcut panel explains the pair. `main.js` had to name the reset keys
explicitly in its `preventDefault` gate, since they are no longer in `keyMap`
and Backspace would otherwise fall through to browser history navigation.

Incidental fix, disclosed rather than folded in silently: `highlightButton()`
and `unhighlightButton()` index a lowercase lookup table with `normalizedKey`,
which preserves case for named keys, so `'Escape'` never matched `'escape'` and
the RES cap never animated. Lowercasing the lookup fixes RES and, with it, the
identical miss on Arrow Up, Arrow Down and Enter. No key mapping changed.

### Scope

`HLT` is left alone. The manual describes it as generating a CPU-level
interrupt, the emulator maps it to matrix position `[2, 3]` shared with DA/RUN,
and the `P` binding is inferred from board position rather than confirmed
against the ROM. That is a separate fidelity question, now noted in
`NextSession.md`.
