## Port A After a Store Past a Row's End

### Purpose and scope

Codex's automated review of pull request 58 (`develop` into `master`, at
`8c8a9dc`) made two findings. This is the first, which was right. The
second is in the next entry.

`compiler/compile.js` drops what it knows about Port A's direction after a
store that may reach the 8255, at `$FD00-$FDFF`, so that the next key read
writes the input mode word again. For a store into a row by a variable
index it took the store's reach to be the row's declared length. The
README says, and the code does, that a variable index is not checked: past
the row's end it reaches whatever byte the instruction addresses. So a row
that stops short of the page could still write a mode word into it, and
the compiler would not know.

### What changed

- `compile.js`: a store by a variable index reaches 256 bytes from the
  row's first. A row that starts at `$FC01` or above now costs a mode word
  before the next key read, whatever its length. A row in page zero wraps
  inside the page and is unaffected.
- `tests/compiler.test.js`: Codex's program, `byte r[4] at $fcfc`, `i = 7`,
  `r[i] = $89`, run on the board, with Port A's direction read on entry to
  `$FF57`; and the two edges, a one-byte row at `$FC01`, which can reach
  the page, and at `$FC00`, which cannot.
- `compiler/README.md`: a sentence saying so, under Memory and ports.

### Verification

- Reproduced first: before the fix, Port A was an output at `$FF57`, with
  no mode word in the listing.
- `node --test tests/compiler.test.js`: 44 passing.
- The test was tried against three plants, each undone afterwards: the old
  reach, the row's length, and reaches of 255 and 257. It failed on each.
- Every program in `compiler/examples/` compiles to the same listing as
  before the fix. Only a row that starts in `$FC01-$FCFF` changes, and on
  the board that is the cassette PROM, where a store is lost anyway.
