# Engineering Log - 2026-11-19

## Escape the Key Name in the On-Screen Highlight Selector

### Purpose and scope

Found during a security review of the public pages. `highlightButton()` and
`unhighlightButton()` in `main.js` built `.key[data-key="..."]` by placing the
raw `KeyboardEvent.key` inside the selector. The keyup listener calls
`unhighlightButton()` for every key, mapped or not, so releasing `"` produced
an invalid selector and `querySelector()` threw a `SyntaxError` into the
console. (The review first named `\` as well; Chrome showed that an unescaped
backslash does not throw, because the parser closes the broken string at its
end and the selector simply matches nothing.) It was not a security issue: a selector can only find elements,
and `amico.keyUp()` had already run, so the emulated machine was unaffected.

Both functions now pass the name through `CSS.escape()`. Inside a quoted CSS
string the escaped form reads back as the original character, so ordinary keys
(`1`, `+`, `ad`) still match their `data-key` values. The duplicated key tables
in the two functions were left alone to keep the change narrow.

The home page build stamp advances to 2026-11-19 with this commit.

### Verification

`node --check main.js` and `git diff --check` passed, and `node --test tests/`
still passes (77 tests). `main.js` needs a DOM and is not loaded by the Node
tests, so the selector was checked in headless Chrome on a scratch page that
uses the same buttons and the same query: the escaped selector still matches
`1`, `+`, `ad` and `a`, and finds nothing, without throwing, for `"`, `\` and
`Shift`; the unescaped form throws for `"`. The full emulator page was not
driven by real keypresses.

## Add a Content Security Policy to the Public Pages

### Purpose and scope

The same security review found no exploitable issue, but the pages had no
Content Security Policy. GitHub Pages cannot set response headers, so the
policy goes in a `<meta http-equiv>` tag in `index.html` and `guide.html`:

`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
object-src 'none'; base-uri 'none'; form-action 'none'`

The pages already fit it: every script is an external file from the site, with
no inline `<script>`, inline event handler, `eval` or `new Function`, and
nothing is fetched from another origin. Inline styles must stay allowed,
because the board layout uses a `<style>` block and many `style` attributes.
Three directives cannot be set from a meta tag (`frame-ancestors`,
`report-uri`, `sandbox`) and were left out; the emulator has no action that
framing could misuse. The tape download in `debug.saveTape()` clicks a `blob:`
link, which a CSP does not restrict.

`keyboard-test.html` and `keyboard-debug.html` were not given the policy: they
use inline scripts and are already listed for removal in `AGENTS.md`.

### Verification

`git diff --check` and `node --test tests/` passed. In headless Chrome, served
over `http://` and opened as `file://`, `index.html` initialized and ran the
monitor (the PC register advanced into the monitor's scan loop) and logged no
CSP violation; `guide.html` also logged none. In headless Firefox opened as
`file://`, a screenshot shows the display lit, the RUN LED on, the registers
updating and every style applied, so `'self'` matches local files there too.
Safari was not tested, because it has no headless mode.

## Check a File's Size Before the Loader Reads It

### Purpose and scope

Also from the security review. The `Load ROM or tape` handler in `main.js`
read the whole chosen file with `FileReader` before any loader looked at its
size. Every loader rejects an oversized file (a ROM over its 512-byte socket,
a program past `$FFFF`, a tape whose header length disagrees), but only after
the read, so a multi-gigabyte file picked by mistake could stall the tab. Only
the person choosing the file is affected; nothing reaches the page from
outside.

The handler now refuses any file larger than `MAX_LOAD_BYTES`, 128KB, before
reading it, and reports the size through the existing error alert. The largest
file a loader can accept is a tape image of 65,535 data bytes plus its 18-byte
header, so twice the 64KB address space leaves headroom and is not tied to
the tape format's header size.

### Verification

`node --check main.js`, `git diff --check` and `node --test tests/` passed.
`main.js` is not covered by the Node tests, so a scratch copy of `index.html`
(without the CSP, so a test script could be added inline) fed the real
`#rom-file` input four in-memory files in headless Chrome, with
`readFileAsArrayBuffer` wrapped to count reads:

- 200,000 bytes and 131,073 bytes: refused with the size message, never read.
- 131,072 bytes, exactly the limit: read, then refused by `loadProgram()` as
  running past the end of the address space, as before.
- 512 bytes named `monitor.bin`: loaded as the monitor ROM, as before.

The file input was cleared after each pick. The file picker itself was not
operated by hand.
