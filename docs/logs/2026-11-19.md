# Engineering Log - 2026-11-19

## Escape the Key Name in the On-Screen Highlight Selector

### Purpose and scope

Found during a security review of the public pages. `highlightButton()` and
`unhighlightButton()` in `main.js` built `.key[data-key="..."]` by placing the
raw `KeyboardEvent.key` inside the selector. The keyup listener calls
`unhighlightButton()` for every key, mapped or not, so releasing `"` produced
an invalid selector and `querySelector()` threw a `SyntaxError` into the
console. (The review first named `\` as well; Chrome showed that an unescaped
backslash does not throw, because the parser closes the broken string at its
end and the selector simply matches nothing.) It was not a security issue: a selector can only find elements,
and `amico.keyUp()` had already run, so the emulated machine was unaffected.

Both functions now pass the name through `CSS.escape()`. Inside a quoted CSS
string the escaped form reads back as the original character, so ordinary keys
(`1`, `+`, `ad`) still match their `data-key` values. The duplicated key tables
in the two functions were left alone to keep the change narrow.

The home page build stamp advances to 2026-11-19 with this commit.

### Verification

`node --check main.js` and `git diff --check` passed, and `node --test tests/`
still passes (77 tests). `main.js` needs a DOM and is not loaded by the Node
tests, so the selector was checked in headless Chrome on a scratch page that
uses the same buttons and the same query: the escaped selector still matches
`1`, `+`, `ad` and `a`, and finds nothing, without throwing, for `"`, `\` and
`Shift`; the unescaped form throws for `"`. The full emulator page was not
driven by real keypresses.

## Add a Content Security Policy to the Public Pages

### Purpose and scope

The same security review found no exploitable issue, but the pages had no
Content Security Policy. GitHub Pages cannot set response headers, so the
policy goes in a `<meta http-equiv>` tag in `index.html` and `guide.html`:

`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
object-src 'none'; base-uri 'none'; form-action 'none'`

The pages already fit it: every script is an external file from the site, with
no inline `<script>`, inline event handler, `eval` or `new Function`, and
nothing is fetched from another origin. Inline styles must stay allowed,
because the board layout uses a `<style>` block and many `style` attributes.
Three directives cannot be set from a meta tag (`frame-ancestors`,
`report-uri`, `sandbox`) and were left out; the emulator has no action that
framing could misuse. The tape download in `debug.saveTape()` clicks a `blob:`
link, which a CSP does not restrict.

`keyboard-test.html` and `keyboard-debug.html` were not given the policy: they
use inline scripts and are already listed for removal in `AGENTS.md`.

### Verification

`git diff --check` and `node --test tests/` passed. In headless Chrome, served
over `http://` and opened as `file://`, `index.html` initialized and ran the
monitor (the PC register advanced into the monitor's scan loop) and logged no
CSP violation; `guide.html` also logged none. In headless Firefox opened as
`file://`, a screenshot shows the display lit, the RUN LED on, the registers
updating and every style applied, so `'self'` matches local files there too.
Safari was not tested, because it has no headless mode.

## Check a File's Size Before the Loader Reads It

### Purpose and scope

Also from the security review. The `Load ROM or tape` handler in `main.js`
read the whole chosen file with `FileReader` before any loader looked at its
size. Every loader rejects an oversized file (a ROM over its 512-byte socket,
a program past `$FFFF`, a tape whose header length disagrees), but only after
the read, so a multi-gigabyte file picked by mistake could stall the tab. Only
the person choosing the file is affected; nothing reaches the page from
outside.

The handler now refuses any file larger than `MAX_LOAD_BYTES`, 128KB, before
reading it, and reports the size through the existing error alert. The largest
file a loader can accept is a tape image of 65,535 data bytes plus its 18-byte
header, so twice the 64KB address space leaves headroom and is not tied to
the tape format's header size.

### Verification

`node --check main.js`, `git diff --check` and `node --test tests/` passed.
`main.js` is not covered by the Node tests, so a scratch copy of `index.html`
(without the CSP, so a test script could be added inline) fed the real
`#rom-file` input four in-memory files in headless Chrome, with
`readFileAsArrayBuffer` wrapped to count reads:

- 200,000 bytes and 131,073 bytes: refused with the size message, never read.
- 131,072 bytes, exactly the limit: read, then refused by `loadProgram()` as
  running past the end of the address space, as before.
- 512 bytes named `monitor.bin`: loaded as the monitor ROM, as before.

The file input was cleared after each pick. The file picker itself was not
operated by hand.

## Refuse a Cassette SAVE the Tape Format Cannot Hold

### Purpose and scope

Noticed while reviewing the loaders. `saveTapeFromMonitorParams()` accepts any
range with `end >= start`, but `_makeTapeImage()` writes the byte count into a
16-bit header field. The one range longer than that, `$0000-$FFFF` at 65,536
bytes, was saved with a count of 0: SAVE reported success (`$0000-$0001` =
`0000`), and the exported image then failed `loadTape()` with "Tape image
length does not match header".

SAVE now refuses that range before storing anything, with the `$0000 = $FF`
status the routine already uses for an end address before the start, and the
trap's existing `catch` keeps returning to the monitor. The earlier record and
`lastSavedTape` are left untouched. The file format was not changed, so every
existing `.amtape` stays valid: the range only adds ROM and the PIA to a save,
which no program on a 2KB board needs. The user guide's SAVE section now lists
both failure cases, matching its existing LOAD note.

### Verification

`tests/cassette-tape-length.test.js` drives the refused save through the
trapped `$FBBC` entry, checking the return to `$FE22`, the `FF` status, that
no record is stored, and that the earlier good save is still the export
target. It also saves `$0000-$FFFE`, the largest range the format holds, and
loads the image back into a fresh machine. With the fix stashed, the first test
fails on the status byte and the second passes; with it, both pass.
`node --test tests/` passes (79 tests), and `node --check` and
`git diff --check` are clean. The guide change is a sentence of text and was
not checked in a browser.

## Keep the Bench Run/Stop Control in Step with the Machine

### Purpose and scope

The user guide's troubleshooting list warned that after console start/stop
commands "the bench button label may be out of sync". The cause was in
`main.js`: it kept its own `isRunning` flag, which only the bench Run/Stop
button changed. The guide's console examples call `amico.stop()` and
`amico.start()` directly, so after them the label and RUN LED showed the wrong
state, and the Step button, which checked the same flag, ignored clicks on a
machine that was actually paused.

`Amico2000` now has an `onRunStateChange` callback, called by `start()` and
`stop()` only when the state actually changes (so `toggle()` reports through
it too). `main.js` drops `isRunning`, reads `amico.running` for the label, LED
and Step button, and sets the RUN LED through the callback at startup instead
of by hand. RES still does not touch the run state (#30). The guide's warning
is removed.

### Verification

`tests/run-state.test.js` checks that `start()`, `stop()` and `toggle()` each
report once, that redundant calls and RES report nothing, and that RES leaves
a running machine running; with the `amico2000.js` change stashed all four
fail. `node --test tests/` passes (83 tests), and `node --check` and
`git diff --check` are clean. In headless Chrome, a scratch copy of
`index.html` with the CSP removed (so a test script could run inline) showed
the label and LED following console `stop()` and `start()` and two bench
clicks, and Step advancing PC from `$FE22` to `$FE24` after a console stop.

## Derive the Keypad Map from the Monitor's Key Decode

### Purpose and scope

`AGENTS.md` asked for the `keyMap` comments to be reconciled with the table,
and for a note that some function keys "intentionally share matrix positions
because the monitor ROM disambiguates them by context". Checking that claim
against the ROM showed the table itself was wrong.

GETKEY at `$FF57-$FF7D` selects rows with Port B = 1, 3, 5 and returns
code = 7 x row + (6 - bit) for the pressed key, as both a hand trace and
running the routine for each of the 21 cells confirmed. The main loop
dispatches the five function codes at `$FE5B-$FE6D`: `$10` sets `$FF = 1`
(AD, address entry), `$11` sets `$FF = 0` (DA, data entry), `$12` increments
the address with auto-repeat, `$13` restores the saved registers and RTIs to
the displayed address (RUN), and `$14` reloads the address from `$00F6/$00F7`.
The manual's key list confirms `$14` is REG ("Registro Program Counter") and
says HLT "genera una interruzione a livello CPU", so HLT is an interrupt line,
not one of the 21 matrix cells. Nothing in the ROM tells keys apart by
context; the codes are fixed per cell.

Against that decode the old table put `0` on REG's cell, AD and REG on RUN's,
and RUN and HLT on DA's, leaving the real `0` and AD cells unused. Typing on the
running monitor in Node showed the effect: `AD 0200` set address `$0000`, AD
pressed after data entry ran the code at the displayed address, and
`AD 0300 RUN` never ran the program. It went unnoticed because the monitor
starts in address mode, so a mis-wired AD followed by non-zero digits still
looked right, and the user guide already steered people to the console.

The new table follows the decode (the comment above `keyMap` shows the grid
and the dispatch addresses). `P` no longer maps to anything, and the on-screen
HLT key no longer presses a matrix cell; HLT is documented as not emulated
because the manual does not say which interrupt line it drives. Docs updated
to match: the README keyboard table and usage notes (REG recalls the saved PC;
the "don't press AD twice" warning was an artifact of AD being RUN), the guide's
key table and its keypad warning, the board's key tooltips and shortcut table,
the keyboard sections of `AGENTS.md` (with the pending comment cleanup
removed), and the machine-fidelity bullet in `NextSession.md`.
`archived/GEMINI3.md` has a third table that also disagrees with the decode;
`AGENTS.md` now says so.

### Verification

`tests/keyboard-matrix.test.js` now runs GETKEY in the emulated monitor for
every key in `keyMap` and checks the code it returns, checks the no-key code
`$15`, and types on the running monitor with 80ms presses: the guide's
seven-byte example entered with AD/DA/+ and run with AD/RUN, AD after DA
returning to address entry, the manual's REG then RUN sequence, and the HLT
button leaving the matrix untouched. With the old `amico2000.js` five of the
seven checks fail; with the fix all pass, and `node --test tests/` passes
(90). `node --check` and `git diff --check` are clean.

In headless Chrome, a scratch copy of `index.html` (CSP removed for an inline
test script) typed the guide's example through `keydown`/`keyup` events on the
document and then clicked the on-screen AD, 0, 2, 0, 0 and RUN keys: the seven
bytes landed at `$0200` and the program stored `$42` at `$0020`. Headless
Chrome does not fire `requestAnimationFrame` under virtual time, so the harness
stopped the frame loop and drove `cpu.run()` from a timer; the key handling in
`main.js` and `amico2000.js` was the real code. Nobody pressed physical keys
on a real keyboard.

## Cross-Reference the Two Memory Initializations

### Purpose and scope

The last pending source-level cleanup in `AGENTS.md`. `CPU6502`'s constructor
fills all 64KB with `$FF`, and `Amico2000.reset()` then clears `$0000-$07FF`
to `$00` because the monitor expects cleared RAM. Both are intentional, but
each comment read as if it alone decided what a program sees. Each now points
at the other: the CPU comment says the AMICO's RAM is cleared by the machine
layer and the `$FF` fill survives above `$07FF` and in standalone CPU use; the
reset comment says it deliberately overrides that fill.

The same comment block in `reset()` labelled `$03FC` as the IRQ vector and
`$03FE` as NMI. The ROM's hardware vectors say the reverse: `$FFFA` (NMI) holds
`$FE1C`, which is `JMP ($03FC)`, and `$FFFE` (IRQ/BRK) holds `$FE1F`, which is
`JMP ($03FE)`. The labels are corrected; the code seeds both with `$FE30`, so
behavior is unchanged. The `AGENTS.md` source-level list is now empty.

### Verification

The vector bytes were read from `MONITOR_ROM` in Node: `$FFFA` -> `$FE1C`,
`$FFFC` -> `$FE22`, `$FFFE` -> `$FE1F`, with `6C FC 03` at `$FE1C` and
`6C FE 03` at `$FE1F`. No other document assigns the two vectors. Comment-only
change: `node --check` on both files, `node --test tests/` (90) and
`git diff --check` pass.

## Say Which Date the Build Stamp Uses

### Purpose and scope

The automated review on PR #40 flagged the build stamp `20261119` as P1,
saying the reviewed commit's committer date was 2026-11-20. That is the UTC
date: the commit was made at 21:46 -0800 on 2026-11-19, which is 05:46 UTC on
the 20th. `AGENTS.md` asks for the committer's calendar date and names
`git show -s --format=%cs HEAD`, which prints the date in the committer's own
time zone, 2026-11-19, so the stamp was correct and is unchanged. The rule
now says explicitly that the date is local, not UTC, and why a UTC comparison
reports a false mismatch.
