# Engineering Log - 2026-11-23

## The Handheld Layout on Tablets Held Upright

### Purpose and scope

The home page build stamp advances to 2026-11-23 with this commit.

The owner tried the page on two more devices. In Chrome on a OnePlus 7T, an
Android phone held upright, the handheld layout looked right and everything
worked. On an iPad Pro 11" held upright the page showed the board as drawn,
with keys and displays "pretty small"; in landscape it "looks ok".

The layout's media query stopped at 640 px. That left tablets out on
purpose, on the reasoning that a screen the board fits should keep the
board, and `tests/handheld-layout.test.js` held the width below the board's
minimum of 760 px for that reason. The iPad shows the reasoning was wrong:
the board fits, but too small to use with a finger.

Measured in headless Chrome, emulating each size as a touch screen:

| Screen, held upright | Width | Key, as drawn | Displays, as drawn | Key, handheld | Displays, handheld |
| --- | --- | --- | --- | --- | --- |
| iPad mini | 744 px | 31 px | 182 px | 94 px | 480 px |
| iPad Pro 11" | 834 px | 32 px | 188 px | 99 px | 480 px |
| iPad Pro 13" | 1032 px | 39 px | 235 px | 114 px | 480 px |
| iPad Pro 11", landscape | 1194 px | 45 px | 268 px | (not used) | |

Landscape, at 45 px a key, is what the owner found fine, so the line falls
between the widest tablet held upright and the board in landscape.

### Change

- `HANDHELD_QUERY` in `main.js` is `(max-width: 1100px)` instead of 640,
  still with `(orientation: portrait)` and `(pointer: coarse)`. Nothing in
  the styles changed: the key pitch, `min(19.5cqw, 9svh)`, already holds the
  keys to the screen's height, and the displays to `max-width: 30rem`, so
  the column fits the first screen of each tablet with room to spare.
- The test now asks that the width take in 1032 px, the widest tablet held
  upright, and says why.
- The guides, in both languages, and the README say "a phone or a tablet
  held upright", and "keys sized for a finger" for "for a thumb". The
  Italian is "un telefono o un tablet" and "a misura di dito"; "tablet" is
  the ordinary Italian word, there being none in the manual.
- AGENTS.md, Handheld Layout and Known Limitations, and NextSession.md,
  item 2, record the OnePlus 7T, the iPad and the reason for the new width.

### What it does not settle

- The owner tried it on the iPad Pro 11" held upright the same day: it looked as intended, a full pass. Other tablets were checked in emulation only.
- On a tablet the title keeps its compact phone size and the language link
  its two letters, and the keys take about half the screen's width. That
  fits, and on the iPad the owner found it right.
- An iPad with a trackpad or mouse attached may report a fine pointer and
  keep the board as drawn. Not tried.

## Checking the Site for Search Engines

### Purpose and scope

The owner asked for the site to be checked for search engines. The live
site was fetched with `curl`, and rendered in headless Chrome with
Googlebot's phone user agent, at `https://ascasso.github.io/amico2000/`.

### What was wrong

**The repository's documents were published as web pages.** The Pages build
is the legacy one, from `master`, and with no `.nojekyll` it runs Jekyll.
Jekyll leaves an HTML file without front matter alone, which is why the
three pages are served byte for byte as committed, but it renders every
Markdown file: `/AGENTS.html`, `/NextSession.html`, `/CHANGELOG.html`,
`/docs/logs/2026-11-23.html`, `/docs/monitor-rom-review.html`, the text of
the supplement and the rest answered 200 as pages in the default theme, each
with a title such as "AGENTS.md | amico2000", the repository's description
and a canonical address of its own. 22 of the 26 Markdown files; the other
four are READMEs, three of which are served as their folder's index.
Nothing on the site links to them, so Google may never have found them, but
a single link from anywhere would put the guidance for agents into the
results for the machine's name. `robots.txt` said the rest of the repository
"is not served as pages".

Fixed with an empty `.nojekyll` at the root. The documents are then served
as the plain files they are, and stay readable on GitHub. `_config.yml` with
an `exclude` list would have taken them off the site altogether, at the cost
of a build to configure where the project has none. It takes effect when
`master` has it.

## Compiling a byte language for the original board

The owner chose the small language sketched for the AMICO and asked for both
assembly and machine code, with the monitor's known bugs taken into account.
The first compiler runs in Node.js. Code and tables fit below the vectors on
a 1 KB board. A listing pairs each instruction with its address, bytes and
source line. The cassette output uses the emulator's own record writer so
the monitor can load the image at its linked address.

The ROM remains the reference. Startup clears D, TASTO gets Port A as an
input, and normal exit enters the monitor through its initialization. A
program can request a shared debounced input routine that scans the displays
while it waits. The compiler guide records the two branch-calculator defects
that a user can still encounter at the monitor.

The square-table program occupies 40 bytes at $0200-$0227. The eight compiler
tests cover all sixteen keys through the monitor after a tape LOAD and a RUN
with D set in the saved status, held and bouncing keys, branch distances,
zero-page temporaries, and the 508-byte limit. All 245 repository tests
passed. Independently assembled the listing with 64tass 1.60.3243 in a
temporary directory and compared the binary byte for byte. Syntax and diff
checks passed. Machine checks used the emulator in Node; a physical board
and the browser file picker were not exercised.

## Playing the matchstick game in the byte language

Added a complete game to exercise the language beyond a lookup table.
The manual supplies the rules and the six-digit arrangement. This version
has a fixed opening reply and uses the debounced input routine instead of
the original delay. It occupies 186 bytes at $0200-$02B9 and uses five bytes
in zero page, including the helper's two. The candidate transcription of
the original listing occupies 148 bytes.

The regression check starts the game with the monitor keypad, rejects 0 and
F, plays a winning and a losing sequence, checks each remaining total, and
reads both final patterns from the emulated displays. All 246 tests passed.
64tass 1.60.3243 assembled both examples to binaries identical to the
compiler's output. JavaScript syntax and diff checks passed.
