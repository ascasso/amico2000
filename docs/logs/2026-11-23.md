## Compiling a byte language for the original board

The owner chose the small language sketched for the AMICO and asked for both
assembly and machine code, with the monitor's known bugs taken into account.
The first compiler runs in Node.js. Code and tables fit below the vectors on
a 1 KB board. A listing pairs each instruction with its address, bytes and
source line. The cassette output uses the emulator's own record writer so
the monitor can load the image at its linked address.

The ROM remains the reference. Startup clears D, TASTO gets Port A as an
input, and normal exit enters the monitor through its initialization. A
program can request a shared debounced input routine that scans the displays
while it waits. The compiler guide records the two branch-calculator defects
that a user can still encounter at the monitor.

The square-table program occupies 40 bytes at $0200-$0227. The eight compiler
tests cover all sixteen keys through the monitor after a tape LOAD and a RUN
with D set in the saved status, held and bouncing keys, branch distances,
zero-page temporaries, and the 508-byte limit. All 245 repository tests
passed. Independently assembled the listing with 64tass 1.60.3243 in a
temporary directory and compared the binary byte for byte. Syntax and diff
checks passed. Machine checks used the emulator in Node; a physical board
and the browser file picker were not exercised.

## Every Small Program Against an Oracle for the Two Flow Rules

The second harness kept from the check, Claude Fable's, rewritten for the
repository as `tests/compiler-assignment.test.js`.

The random programs of the entry above are all valid, so they say nothing
about what the compiler should refuse. This test makes every program of up
to five statements out of an assignment, a read, `stop`, `loop` and `if`
with and without `else`, nested up to three deep, over one name, and every
one of up to four statements over two names: 35,662 and 9,136 programs. For
each, an oracle says whether it is valid and, if not, the line of the first
statement that is wrong and why.

The oracle does not work as the compiler does. The compiler walks the
source, keeps a set of assigned names, and intersects two sets where the
arms of an `if` meet. The oracle builds a graph of statements, finds what
can be reached by search, and finds the names certainly assigned at each
node by going round the graph until nothing changes. A loop is an edge back
to its first statement; `stop` is a node with no way out.

The compiler has to agree on all of them: accept the 5,974 and 1,844 valid
ones, and refuse each of the others with "Line N:" for the same line and
with "Unreachable statement" or "assigned variable" in the message. The test
also holds the four counts, so that an enumerator which stopped short would
be noticed. 0.3 s. `AMICO_STATEMENTS=7` is 5.6 million programs, 4.1 million
with one name and 1.5 million with two.

Verification. Passes on the compiler as it is. Against a scratch copy in
which the arms of an `if` are not intersected, so that a name assigned in
one arm counts as assigned after both, it fails. `node --check`,
`node --test tests/` with 251 passing, `git diff --check`.

## A 257-Byte Program and the Cassette PROM

The first of the check's findings to be fixed (`NextSession.md`, item 13).

The cassette PROM loses the last byte of a block one byte longer than a
whole number of pages (`AGENTS.md`, Cassette Sound Format). The emulator has
always known that: the sound codec notes it and the traps keep the byte on
purpose. The compiler did not, and when a program came to exactly 257 bytes
its last byte, the high half of the closing `JMP $FE22`, never reached the
board through the real routine. Loaded with Cassette: Real time, such a
program ran into `JMP $0022`.

`emit.js` now lays the image out, and if its length is one more than a
multiple of 256 adds one `$EA` after everything else and lays it out again.
Nothing executes the byte, and adding it at the end moves nothing. The
listing says what it is for. `$EA` is what the manual's own long listing
fills with, before the vectors (supplement, page 99). On this board the only
such length under the 508-byte limit is 257; the rule is written for any,
since programs that step over the vectors will reach 513 and beyond.

The test builds a program of 257 bytes (CLD, three scans, sixty-one
assignments and the JMP), checks that it comes out at 258 with the filler
last and that programs of 256 and 258 bytes are left alone, and loads it
with the PROM's own LOAD routine against the emulated recorder: all 258
bytes arrive. Then it loads the same image without its filler, and the last
byte does not arrive, which is the fault itself.

Verification: `node --check compiler/emit.js`, `node --test tests/` with 252
passing, `AMICO_PROGRAMS=5000` on the differential test, `git diff --check`.

## A Source File With CR-Only Line Endings

The second finding. `compile.js` split its source at LF, with an optional CR
before it. A file whose lines end in a CR alone, which is how Mac OS wrote
text until 2001 and how some editors still can, was therefore one line. Two
things followed. A `#` anywhere in it made a comment of the rest of the
file, statements included, and the compile went through with a program cut
short. Without a `#`, the one line matched nothing and the error message
quoted the whole file.

The split is now at CR LF, at CR, or at LF, in that order, so that CR LF is
one ending and not two. Line numbers in errors count CR lines as lines.

The test compiles `squares.amico` with each of the three endings and wants
the same 40 bytes; compiles two assignments with a comment on the first,
ended by CRs, and wants both in the code; and wants an error on the second
CR line to say "Line 2".

Verification: `node --check compiler/compile.js`, `node --test tests/` with
253 passing, `git diff --check`.

## Three Messages That Named the Wrong Mistake

From the check's fifth finding. Each of these was refused, rightly, with a
message that sent the reader to look at something that was not wrong.

- **A comparison with an operation on its right.** `CMP` wants the left side
  in A and the right side as one operand, so `if b + 1 == a` compiles and
  `if a == b + 1` does not. The message for the second listed the four
  operators, of which `==` is one. When the operator is one of the four and
  the rest of the line holds no other comparison sign, the message now says
  that the right side is one literal, variable or display field and that an
  operation, a table read or a key read goes on the left. `<=` and `>` still
  get the list of operators, which is what is wrong with them.
- **A word of the language as a name.** `byte = 7` and `in = keypad.read()`
  were "Invalid byte variable". The message now says the word is one of the
  language's.
- **A table declared twice**, and a table's name assigned to, which were the
  same "Invalid byte variable": "Table declared twice" and "is a table, not
  a variable".

`compiler/README.md` gives the rule for the two sides of a comparison and
lists the eleven words. The test reads the compiler's own list out of
`compile.js` and fails if the README lacks one of them.

Verification: `node --check compiler/compile.js`, `node --test tests/` with
254 passing, among them the oracle for the two flow rules, whose messages
were left as they were; `git diff --check`.

## A Misspelt Line After `stop`

Also from the fifth finding. The compiler asked whether a statement could be
reached before it asked whether the line was a statement at all. So `ennd`
on the line after a `stop` was "Unreachable statement": true of anything
there, and no help to someone looking for a missing `end`. The question
whether the line is one of the statements now comes first, and a line that
is none is "Unknown statement" wherever it stands. A real statement after
`stop` is unreachable as before, and the oracle test, which tries only real
statements, is unaffected.

## `display.hold()`

The third small fix.

A program that ends, by `stop` or by running off its last line, goes to the
monitor's reset entry, and the monitor at once puts its own address and data
on the displays: `0000` and the byte at `$0000`. So a program could not end
with a result showing. The examples and the tests already knew the way round
it, `loop`, `display.scan()`, `end` as the last three lines.

`display.hold()` is those three lines as one statement: a label, `JSR $FF0C`
and a jump back, six bytes, the same six. Nothing after it is reached, and
the compiler treats it as it treats `stop`: a statement after it is
unreachable, and in one arm of an `if` the program goes on by the other.
`matches.amico` now ends its game with it; the image is the same 186 bytes.

The README says under `stop` what the monitor does to the displays, and
sends the reader to `display.hold()`.

Tests. `tests/compiler.test.js` starts two programs with the monitor's keys:
the one that stops reads `0000 00` straight away, the one that holds reads
`1234 56` through four key presses and a second of board time, until RES.

same verdicts. The reference interpreter takes it for the end of the program.

back gives no moment at which to read the board; its header says so.

## What HLT Does to the Display Fields

The fourth small fix, and the last: a note in the compiler's README and a
test that pins what it says.

`display.high`, `display.low` and `display.data` are three bytes of the
monitor's own workspace, `$FB`, `$FA` and `$F9`. HLT is the monitor: its
routine at `$FE00` copies the halted program's address into the first two,
and its scan then copies the byte at that address into the third. RUN
restores the registers and returns into the program; it does not restore
those three bytes. The NOR/SS switch at SS goes through the same routine
after every instruction, so the fields are overwritten at every step: after
the first step of a program at `$0200` they read `0201` and the byte there.

A program that keeps a count or a state in a display field, as the 1979
clock does and as the matchstick example does with its first move, has lost
it after a halt. The README says so under Display and keys, with the advice
to keep what matters in a variable and write the field from it.

The test halts and resumes two programs. One sets the three fields once and
holds: after RUN the first two still hold the halted address. The other
writes them from a variable every round: after RUN they are right again.

Verification: `node --test tests/` with 265 passing; single step tried by
hand in Node, as quoted above; `git diff --check`.

## A Name for a Memory Location

The second addition, and the one the rest hang on.

**What it is.** `byte sum at $04` gives the byte at an address a name.
Reading the name is a load from that address and assigning to it is a store
there; in page zero the instruction carries one byte of address, above it
two, and `emit.js` has the absolute forms of the eight instructions that
needed them. The address is a literal up to `$FFFF`. It is declared before
the first statement, like a constant or a table.

**Never remembered.** For its own variables the compiler skips a load when
the value is still in A. A named location is read every time it is named and
written every time it is assigned to, and is never taken to be in A: it may
be a port, which does not give back what was put into it, or a byte that the
monitor or the person at the keys changes. After a store, A is still known
by what was stored, a number or a variable, since the store did not change
it.

**Not in `$20-$7F`.** The compiler puts the program's own variables there in
the order it meets them. A name fixed among them would share a byte with one
of them without either being told, so an address in that range is refused.

**What it makes possible.** The manual's first program (Tabella 7, page 31)
adds the bytes at `$06` and `$07` into `$04`, and is `18 A5 06 65 07 85 04
4C 22 FE`. In Amico it is three declarations and `sum = a + b`, and compiles
to `D8 A5 06 18 65 07 85 04 4C 22 FE`: the manual's ten bytes, the `CLC`
after the load, and a `CLD` in front. With decimal mode left set by an
earlier program, the manual's bytes add 09 and 01 to 10 (the monitor review,
bug 1); these give 0A. Keyed in through the monitor on the emulated board,
`AD 0006 DA 09 + 01`, `AD 0200 RUN`, `AD 0004` shows `0004 0A`. And the LEDs
D4-D7 light by naming the 8255's mode register and two ports, as the README
now shows.

**The tests' other half.** The reference interpreter keeps the board's
memory by address now, so that the display fields, at `$FB`, `$FA` and
`$F9`, which the README states for the purpose, and the named locations are
bytes of one memory, and two names for one byte are one byte. The
differential test fills all 2 KB of RAM with junk before each program and
compares all of it afterwards with what the interpreter says, where it used
to compare the display bytes and check the rest was untouched. Half the
generator's programs name locations: one in page zero, often one in the
second kilobyte, and often a third that is sometimes a second name for the
first one's byte, or for a display field's.

Three defects were planted. An address cut to its low byte fails the random
programs. A location remembered in A under its own name, after a read or
after a write, passes them all: in plain RAM, where every write goes through
A, that is never wrong. It is wrong for a port and for a PROM, and
`tests/compiler.test.js` has both: two readings of `$FD00` must be two
loads, also straight after a comparison, and a byte stored into the monitor
PROM must read back as the PROM's.

Verification: `node --test tests/` with 269 passing; the differential test at

## A Call to an Address

The third addition.

`call $ff7e` is a `JSR` to the address, which is a literal up to `$FFFF` as
for a memory name. `call` becomes a word of the language. When the routine
comes back the compiler takes nothing to be known: not what is in A, and
not which way Port A has been left, so that a key read after a call writes
the mode word again. That is the one difference from `display.scan()`, which
is a call to `$FF0C`: the compiler knows that routine ends with Port A an
input, and knows nothing of any other. Code after a call is reachable; a
routine that does not return is the caller's business.

With the two additions before it, this reaches the monitor's routine D at
`$FF7E`, which shows the six bytes at `$8F-$94` as raw segment patterns. The
supplement's exercise on PDF page 68 does that for the word ASEL, `77 6D 79
38 00 00`, with `20 7E FF 4C 00 03`. The test writes it as six names, six
assignments and a call in a loop, starts it with the monitor's keys, and
reads `77 6D 79 38 00 00` from the emulated displays. It is clumsy with a
name to a byte; the row of bytes that comes next is for exactly that.

The random generator does not write `call`, since what a routine does to

## A Row of Bytes

`byte segment[6] at $8f` names six bytes at once, and `segment[i]` is one of
them, to read or to assign to.

**A literal index** is checked against the count and becomes a plain
address, so `segment[2] = $79` costs what a single named byte costs. A
constant counts as a literal here as everywhere.

**A variable index** goes through X and is not checked. To read, the index
is loaded as any value is and moved over, `TAX`, then `LDA $8F,X`. To store,
the value is worked out into A first, X is then loaded on its own, `LDX`,
which the assembler half now has, and `STA $8F,X` follows. The other way
round, the index would be lost when the value was worked out through A.

**Page zero.** A row that lies wholly in page zero uses the instructions
with one byte of address. A 6502 address indexed that way wraps round inside
page zero, so a row that runs from `$F8` into `$0107` uses the two-byte form,
or its ninth byte would be reached at `$0000`.

**Limits.** 1 to 256 bytes, which is as far as a byte can index; not past
`$FFFF`; and not over `$20-$7F`. The count may be a constant. A row may lie
over a named single byte or over another row: they are then the same bytes.
A table cannot be assigned to, and the message for trying says so.

The manual's word, copied from a table into the row by a counter and then
shown with `call $ff7e`, is twelve lines; with a literal index on each line,
ten lines and 29 bytes. The supplement's own version keys the six bytes in
by hand and has six bytes of program.

**The tests' other half.** The reference interpreter knows a row by its
address and count. Four programs in ten from the generator name a row or
two, one wholly in page zero and one above it, and read and write bytes of
them by a literal and by a masked variable, and compare one on the left of
an `if`; 31% of the programs that run use one. Four defects were planted in
scratch copies: a literal index one byte too high, a store that does not
give X the index, a read that does not, and A left known by the index's
name after a read. The random programs fail all four.

## The Compiler Reads a Line as Pieces

The next step agreed for Amico is `for`, `break` and `next`, and conditions
joined by `and` and `or`. The compiler read a line with a regular
expression for each shape a statement can have, nineteen of them by now, and
a condition of several comparisons is more than one of those can take apart.
So the reading was changed first, on its own, with nothing added to the
language.

`pieces()` in `compiler/compile.js` splits a line into three kinds of piece:

- a term, which is a number or a name: letters, digits, `_` and `$`, and a
  dot where it has one of those on both sides, so that `display.data` is one
  term and the two dots of `0..15` are never part of one;
- a mark: an operator, a bracket or a comma, those of two characters looked
  for first;
- any other character, by itself, for whichever statement meets it to
  refuse.

Each piece keeps where it stands in the line, so a message still quotes the
line as it was written, spaces and all. A statement is recognised by its
pieces, and the parts of it that are a value or an expression go on to the
same functions as before, as text. The regular expressions that are left
are small ones: what a number or a name looks like, and whether a piece of
text is one run of characters.

**That nothing changed was measured, not assumed.** A copy of the compiler
as it stood at `6d19d1a` was run beside the new one on the five examples,
on 20,000 programs from the differential test's generator, and on 600,000
variants of valid programs with one to three edits each: a character
deleted, inserted or replaced, a word of the language dropped in, two lines
swapped. Of those, 148,235 were accepted by both, and for every one the
bytes, the listing and the warnings were identical. No source that was
accepted is now refused. One form that was refused is now accepted: `byte
row[6]at $8f`, with no space between the bracket and `at`, which is how
spacing works everywhere else in the language.

The other differences, some 6,000, are all in which message a malformed line gets,
and each kind was read. Typical: `display.=can()` was an invalid variable
and is an unknown statement; `byte, sum at $04` was an unknown statement
and is told what a `byte` line looks like; `if cnt= != 251` was told that
`cnt=` is no value and is told what a comparison looks like. One kind was
worse in the first draft and was put back: `if rounds ==.0` had been told
that `.0` is no value, and the draft told it that the right side of a
comparison is a single value, which it nearly is.

## `for`, a Loop That Counts

The first of the words the owner chose for loops (The Words for Leaving a
Loop, above): `for i in 0..5`, closed with `end`. Three things were left to
be settled when it was built, and are settled so.

- **The two ends are literals or constants.** The language has no run-time
  checks, by the list of what stays out. A `for` whose last value was a
  variable would need one, or would do something nobody wrote when the first
  value turned out the greater: run on through 255 and round. With both ends
  known the compiler knows the count, the loop always runs at least once, and
  nothing is left to go wrong on the board. A count that varies is a `loop`,
  and `break` is its way out.
- **It counts down when the first value is the greater**: `for i in 5..0`.
  No word is needed for it, since both ends are numbers on the line and the
  direction can be seen. A row of bytes moved one place towards its end has
  to be copied from the far end backwards, or each byte overwrites the next
  before it is read.
- **Afterwards the name is one step past the last value**: 6 after `0..5`,
  and 255 after `5..0`, because a byte wraps. It is what the code leaves,
  since the foot of the loop steps the count and then compares it. Once
  there is a `break`, a name that is not past the end will say where the
  loop was left.

And one rule that was not on that list: **inside its own loop the name
cannot be assigned.** The foot of the loop goes round until the count is
exactly one past the last value. A program that moved the count past it
would run on through 255, and the compiler can see such an assignment where
the board cannot. Outside the loop the name is a variable like any other.
The count is a variable of the program's own, not a display field or a
named location, which the monitor or something else might change.

What it compiles to, for `for i in 0..5`:

```
    LDA #$00
    STA var_i
flow_1:
    ...
    INC var_i
    LDA var_i
    CMP #$06
    BNE flow_1
```

Twelve bytes besides the statements. The count is in the accumulator at the
top by both ways in, so the compiler takes it to be there and a first
statement that reads it loads nothing. Downwards the step is a `DEC` and the
compare is with one below the last value. A loop whose statements never
reach its foot, because they end in `stop`, gets no step.

How it is tested.

- `tests/compiler.test.js` pins the bytes and runs loops on the board: up
  and down, one value, the whole of a byte both ways, the order of the
  values, constants for ends, one loop inside another, and the README's
  three-line copy of the manual's word, read off the displays. It holds
  thirteen refusals to their messages.
- The reference interpreter and the generator of random programs have `for`,
  from the README's description of it: 64% of the programs that fit the
  board now have one, and 20,000 of them agreed with the board.
- The oracle for the two flow rules has `for` as two nodes, the statement
  and the step at its foot. It and the compiler agree on all 187,126
  programs of up to five statements, of which 26,321 are valid.
- Twelve defects were planted in a scratch copy, one at a time. Ten were
  caught. The two that were not showed two things no test asked: that a
  loop which never goes round has no step, and that a name which counts a
  `for` is not warned of as never read. Both are tested now.

## `break` and `next`

The other two words the owner chose. `break` leaves the loop it is in and
`next` goes round it again; both concern the innermost `loop` or `for`, and
each compiles to one `JMP`.

Until now the only way out of a `loop` was `stop`, which ends the program,
and the compiler refused any statement after a `loop` as unreachable. That
rule is now this: what follows a loop is reached through its `break`s, and
in a `for` also when the count is done. So:

- after a `loop` with no `break` there can still be no statement;
- nothing can follow a `break` or a `next` in its own block;
- a name can be read after a loop only if every way out of it had assigned
  it. For a `loop` the ways out are its `break`s. For a `for` they are its
  `break`s and its foot, and the foot is reached from the end of the
  statements and from each `next`.

No going round is needed to work that out. The names assigned at the top of
a loop are those assigned on the way in: every way back to the top has
passed through the top, and a path only ever gains names. The compiler goes
down the source once, as before, and keeps for each open loop the sets of
names its `break`s and `next`s were reached with.

`break` or `next` outside any loop is refused wherever it stands, before the
compiler asks whether the line can be reached, as a line that is no
statement is.

**The cost of `if ... break`.** A condition and a `break` come out as a
branch over a jump, five bytes, where someone writing by hand would branch
straight out in two:

```
    CMP #$05
    BNE flow_2
    JMP flow_4
flow_2:
```

That is left for the step already agreed as tighter code. It is the same
shape an `if` with only a `stop` in it has always had.

How it is tested.

- `tests/compiler.test.js` runs both words in both kinds of loop on the
  board, one loop inside another, the README's search of a row of bytes for
  a key's code, found and not found, and the README's key program with keys
  pressed on the emulated keypad. It holds seventeen refusals to their
  messages.
- The reference interpreter and the generator have both words. Half the
  random programs that fit the board now have a `break` and a fifth a
  `next`, in the arms of `if`s inside both kinds of loop, with statements
  after the loop; 20,000 of them agreed with the board. The generator's
  loops that count at their foot take no `next`, which would pass over the
  counting and never end.
- The oracle has the two edges. It and the compiler agree on all 457,408
  programs of up to five statements made of `if`, `else`, `loop`, `for`,
  `break`, `next`, `stop`, assignments and reads, of which 36,545 are valid;
  and at six statements too, which takes 75 seconds and is not the default.

## `>` and `<=`

The language had four comparisons, the four that the 6502's `CMP` answers
with one flag: carry for `<` and `>=`, zero for `==` and `!=`. A program
that wanted `x > y` had to turn it round by hand, and could not when the
left side had to be the operation. The other two are in now.

- Against a variable, a display field or a named location, `>` is not below
  and not equal, `BCC` and `BEQ` both leading away; `<=` is equal, or else
  below, a `BEQ` over a `BCS`. Two branches, two bytes more than the other
  four.
- Against a literal or a constant the compiler takes the next number, as one
  does by hand: `x > 5` is `x >= 6` and `x <= 5` is `x < 6`, one branch.
- 255 has no next number. `x > 255` is never so and `x <= 255` always, and
  either is refused in those words, since what would follow is an arm that
  never runs or an `if` that decides nothing.

The left side is not turned round to save the second branch. It stays in
the accumulator and the right side stays the operand, so the listing reads
in the order of the source, and a location that is a port is read when the
line says.

The message for a comparison that is none now names all six operators, and
a comparison with nothing before its operator is told that it needs a value
on its left, where it was told the operators.

How it is tested: every one of the six comparisons, on the board, for each
pair of the seven values 0, 1, 2, 127, 128, 254 and 255, with the right side
a number, a variable in page zero and a named location above it: 124
programs, each of which compares all seven values in a `for` and notes in a
row of bytes which arm it took. The two that are refused are checked to be.
The generator writes all six, and 20,000 random programs agreed with the
interpreter. Eight planted defects were all caught.

## `and` and `or`

A condition was one comparison, so the matchstick game took three `if`s one
inside another to accept a move, each with its own `end`. A condition may
now be several comparisons, joined all by `and` or all by `or`.

- **Tried in order, and no further than it takes.** With `and`, each
  comparison that fails branches away to where the `if` ends, exactly as the
  nested `if`s did: the bytes are the same. With `or`, each comparison but
  the last branches to the statements when it holds, and the last branches
  away when it does not. So a `keypad.press()` in a later comparison is not
  come to once an earlier one has settled the matter, and the README says
  so, since it can be seen at the keys.
- **Not mixed.** `if a == 1 and b == 2 or c == 3` is refused. Which of the
  two comes first is a rule of precedence or a pair of brackets, and the
  list of what stays out has both. The second question goes in an `if` of
  its own.
- **What is known afterwards.** After an `and`, the statements are reached
  one way only, and the compiler knows what the accumulator holds and which
  way Port A faces. After an `or` they are reached from each comparison,
  with a different left side in the accumulator, and perhaps without having
  come to a key read that would have turned Port A. So after an `or` the
  compiler takes nothing as known.

This is what the reading of a line as pieces was done for: the condition is
split at the words `and` and `or`, which are terms, and a name such as
`band` is another term and is not split.

How it is tested: both words with two and with three comparisons, in six
orders, all eight cases of each, on the board, with a comparison of each
kind in each place, since the last of a chain joined by `or` is compiled as
the others are not; two programs that would wait for a key for ever if a
later comparison were come to; one that reads the wrong byte if the
accumulator were taken as known after an `or`; and ten refusals. More than
half of the generator's programs now have a joined condition, and 20,000 of
them agreed with the interpreter. Nine planted defects were all caught.

## `else if`

The last of the richer conditions. A program that had three cases to tell
apart wrote an `if` inside the `else` of another, and a third inside that:
one more `end` and one more margin for every case. `else if` is an `else`
with a condition of its own, which leaves the `if` open, so that one `end`
closes the whole chain.

It compiles to the same bytes as the nest. In the compiler an open `if`
used to keep one thing, what its first arm had assigned and whether its end
was reached. It now keeps a list: what each arm that reaches the `end` had
assigned, and, when there is no plain `else`, what the `if` started with,
for the way past every condition. A name can be read after the `end` if it
is on every entry of that list.

Two things about what is known:

- Where an `else if` begins is reached from a comparison that failed, with
  that comparison's left side in the accumulator, whatever the arm above
  left there. So the compiler forgets before it compiles the condition.
- What the condition leaves is known to its own arm, as after any `if`.

How it is tested: the README's chain against the nest it stands for, byte
for byte, and run for each of its three cases; a chain of four conditions
and an `else` in which two conditions hold for one value, to show that the
first is taken; a chain with no `else`; conditions joined by `and` and by
`or`; arms that `break` and `next`; and fourteen refusals. The oracle
writes every one of its programs again with each `else` that holds one `if`
and nothing more as `else if`: 398 of the 35,662 programs of up to five
statements have such a chain, and compiler and oracle agree on all of them,
at the lines the shorter source has. A third of the generator's programs
that fit the board now have a chain, and 20,000 agreed with the
interpreter. Eight planted defects were all caught.

The generator's programs are longer for it, and 59% of them fit the board

## Reviewed: Two Separators That Were Spaces

## Reviewed: Two Costs That Assumed a Short Branch

Codex's finding, and a false statement of the session's. The README said
that a `for` adds twelve bytes to its statements, and that `>` and `<=`
against a name cost two bytes more than the other comparisons. Both are
so while the statements are short. A 6502 branch reaches 127 bytes forward
and 128 back; over more, the back end writes the opposite branch round a
`JMP`, five bytes for two. So:

- a `for` whose statements are too long for the branch back adds fifteen.
  Codex's case: 496 bytes of statements, which fit the board, are refused
  as 511 inside a `for`, where twelve would have made exactly 508;
- `>` against a name, whose two branches both cross the statements, costs
  five bytes more than `>=` over long statements, 150 against 145 in its
  case; `<=` costs two more than `<` either way, since only one of its two
  branches crosses.

Nothing in the compiler is wrong, and the refusal at 511 is right. The
README now gives both figures for a `for`, sends the reader of Conditions
to The ROM and the memory budget, and says there what a branch reaches and
what its long form costs, which it had not said anywhere. The tests hold
it to 12 and 15, to 496 and 511, and to the 5 and the 2. The two entries
of the changelog that gave the short figures alone give both.

A count of the session's own went wrong on the way: an assertion that
worked the size of the long `if` out by hand came to 143 where the compiler
gives 145, because the first statement of the arm has to load what the
others find in the accumulator. It was replaced by one that looks for the
long branch in the listing.

## `decimal`, Sums in Two Decimal Digits

The next step of the order of work, which the owner said to go on to: a
`decimal ... end` block, inside which `+` and `-` count in decimal. It was
agreed in those words and with one rule, that the compiler clears decimal
mode around the key routine, where the monitor goes wrong. The rest was
left to be settled when it was built, and is settled so.

- **Which routines are called in binary was found by running them.** Each
  of the monitor's routines that a program calls was run with the decimal
  flag clear and set, noting every `ADC` and `SBC` it executed, and then
  followed statically through every branch from its entry. The scan at
  `$FF0C` and the routine that shows raw segments at `$FF7E` contain no
  sum on any path: 47 and 22 instructions. The key routine at `$FF57` has
  one, the `ADC #$07` at `$FF78` that the monitor review has as bug 2. So
  `display.scan()`, `display.show()` and `display.hold()` are called as
  they are inside a block, which is what the clock of May 1979 does from
  its first instruction to its last, and `keypad.read()` and
  `keypad.press()` are called between a `CLD` and a `SED`. A scan takes
  4,237 cycles with the flag either way.
- **A `call` is made in binary too**, and the block is in decimal again
  when it comes back. The routine is somebody else's and was written to be
  called from the keys. Outside a block a call was already followed by a
  `CLD`; inside one it is `CLD`, `JSR`, `SED`.
- **A `break` or a `next` that leaves the block clears decimal mode**, one
  byte before its jump: it leaves by another way than the `end`. One whose
  loop is itself inside the block does not. `stop` needs none, because the
  monitor's entry at `$FE22` reaches its own `CLD` at `$FEE8` having done
  nothing but load and store.
- **A `for` counts in binary inside a block as outside it.** `INC` and
  `DEC` take no notice of the flag, and the count is most often an index.
- **A number added or subtracted in a block has to be two decimal digits.**
  `x + 10` is the mistake most easily made there, since 10 is `$0A`, and it
  costs nothing on the board to refuse it. What a variable holds is not
  checked, as an index that is a variable is not.
- **A block cannot be inside another.** There is one decimal mode, and the
  inner `end` would clear it for the rest of the outer block.
- **The block is no branch.** Its `end` is reached only from its last
  statement, so what the accumulator and Port A are known to hold there is
  still known after it, and `SED` and `CLD` change neither.

The reference interpreter gained the block from the README: a byte as two
digits, sums modulo a hundred, and an error for a sum of any other byte,
which the language leaves to the 6502. That is also the one place where
the emulator's CPU is known not to do what the chip does
(`docs/6502-conformance.md`), so no test here depends on it. The random
generator keeps three names that never hold anything but two digits and
gives a block's `+` and `-` only those and numbers of two digits; the rest
of what it makes inside a block uses the other three operators. Of 20,000
programs, 57% fitted the board, and of those 54% had a block, 46% a sum in
decimal and 18% a `break` or a `next` that leaves a block. All agreed with
the interpreter. The oracle has the block as a statement whose body leads
where it leads: 110,191 programs with one name, and 47,958 with `for`,
`break` and `next` as well.

On the board, by hand-written tests: every pair of two-digit bytes added
and subtracted, 10,000 of each; the key routine's codes inside a block,
F as `$0F` and no key as `$15`; a routine called from a block that notes
the status it was given; the monitor's keys after a `stop` in a block; and
a program halted in a block with HLT, resumed with RUN, and then the
manual's sum adding 9 and 1 to 10 because the monitor kept the status it
saved, which is the monitor review's bug 1 and is now in the README.

## The 1979 Clock as an Example

  998,754 and the 94 rounds make up the rest. Measured at the top of the
  loop on the emulated board, a second is 1,000,002 cycles; the one that
  turns the minute is 1,000,021, the hour 1,000,040 and the day 1,000,044.
  That is about a fifth of a second a day on a board whose crystal is
  exact, which no board's is: a round of the adjustment is thirteen
  millionths, a little over a second a day.
- The test keys the time in as the file's first lines say, runs the clock,
  and holds a second to within five cycles of a million and a turn to
  within fifty, so that a change to the code a `for` compiles to will say
  that the clock wants setting again. It reads 12:34:59 to 12:35:00, 09 to
  10 in the minutes and in the hours, and 23:59:59 to 00:00:00, and the six
  digits against the time.

HLT loses the time, since the monitor takes the display fields at a halt.
The article's clock has the same weakness.

which has `d = SE`, `F = Fl` and `Spenta = 99` where the page has `5E`,
`F1` and `00`.

- It has the ten digits, the dash, the dark digit, and twenty letters:
  A b C d E F G H I J L n o P q r S t U Y. No K, M, V, W, X or Z.
- Its sixteen hex digits are drawn as the monitor's own table at `$FFEA`
  draws them, which a test compares with bit 7 put aside. The monitor has
  bit 7 set on all sixteen and Tabella 18 on all but b and d, and the
  manual says on the same page "il bit 7 non viene utilizzato". The
  language leaves it clear, as the first ASEL has it, `77 6D 79 38`: seven
  segments, seven bits.
- Its `o` is `BF`, the round of its zero, printed small. Its G is `BD`, a
  capital, which is the G the owner recognised on the emulated displays on
  2026-11-22. Its Y is `EE`, the shape the owner remembers standing for a Z.

What was settled in building it:

- **The manual's alphabet and no more.** A character that is not in it is
  refused by name, and a table written out still holds any pattern. Seven
  segments can draw a small c, h or u, an underline and more, but those
  would be letters of our own, and a program that wants one can write its
  byte. So the machine cannot spell its own name in this alphabet: there is
  no M.
- **One shape to a letter, written in either case.** The table prints a
  letter in the case its shape has. Asking for exactly that case would
  refuse `"CIAO"` for its O.
- **`segments` is not a word of the language.** It means something only
  after `table`, as `at` does after a name, and a program may have it as a
  name.
- **The listing says the text**, in a comment line over the table's bytes,
  since the bytes do not.

The example is the sliding text, `compiler/examples/slide.amico`: 87 bytes,
31 of them a text with six blanks at each end. A step is sixty calls of
`display.show()`, each 4,119 cycles and 13 for the loop, a quarter of a
second.

**A fault of the emulator's turned up in testing it**, and is recorded in
`NextSession.md`, not mended here. `_updateDisplay()` in `amico2000.js`
takes no notice of a blank pattern sent to a digit, because the monitor
blanks the segments between one digit and the next. So a digit that a
program turns from a letter to a space goes on showing the letter until the
tenth of a second of persistence runs out, where a board would go dark at
once. A text that slides four places a second shows a ghost of the letter
before in every place that becomes a space, for four tenths of each step.
The test of the example waits it out.

Tests. On the board, the manual's word from a text and from the table
written out are the same bytes; every character of Tabella 18, typed into
the test as the page prints it with bit 7, comes out as that byte with bit
7 clear, in either case; the sixteen hex digits match the monitor's table;
and the README's list is parsed and held to both. Characters that are
not in the alphabet are each refused by name, 31 of them at first. The example is run from
RUN and its six digits read at every step, round the whole text and on
into the second turn. The reference interpreter has the alphabet a second
time, typed from the README, and one random table in five is a text.

39 defects were planted in a scratch copy, one at a time: fifteen
letters, a digit, the dash and the space given another shape, three
characters added, the quotes, the length, the spaces, the case, the
listing's comment, and four in the interpreter and the generator. 38 were caught at once. The one that was
not took the spaces out of the generator's texts; the differential test
now counts the programs whose text has a space, with a floor, and catches
it. Measuring that floor showed another too tight: a `next` that leaves a
`decimal` block is in 6% of programs, and 300 programs once had it in 5
of 173, under a floor of 3%. It is 1.5% now.

## `table segments` Reviewed: Two Letters Too Many, and the Tests

Reviewed before its push by Codex on Astra, for the code, and a Claude Opus
subagent, for the tests and the documents; the section after this has how
and what was found sound. Each finding was reproduced before anything was
changed.

**One defect in the compiler, found by both.** `"ı"`, the dotless i, compiled
as an I, and `"ſ"`, the long s, as an S: the lookup made a capital of every
character with `toUpperCase()`, and those are the two characters outside
ASCII whose capitals are letters of the alphabet. Codex tried all 1,114,112
code points and Opus the first 65,536; there are no others. Now only the
twenty-six small letters are made capitals. The reference interpreter, typed
separately, had refused both, but no test asked.

**Two messages that pointed at the wrong thing**, from Codex. Something
after the closing quote was told that the text goes between two double
quotes, which it did; it is told now what follows the quote. And `const t =
segments "A"`, with `table` left out, was offered the two kinds of constant
that are not the one meant; the message names the third.

**Tests that let defects through.** Opus planted 40 defects that were not
among the author's 39, and 19 passed every test. Codex planted three, all
of which passed. What they showed missing, and now has a test:

- the characters refused were 31 picked by hand; they are every character a
  keyboard has outside the alphabet, 41, with a tab, a space that is not
  the space, the two letters above, three more that are not ASCII, and one
  that is two units long, which has to be named whole;
- a text of 256 characters was 256 times the same letter, so that the
  second half could have been the first again;
- the word had to be `segments` only to its eighth letter, and anything
  could stand between it and the text;
- a text could take the name of a memory location, and `segments` was
  tried as the name of a variable only;
- a text read by a variable on the left of a comparison was never followed
  by a read of that variable;
- the listing's comment was looked for over one table, with one space in
  it, beside no other table: its line number, two spaces together, a
  second text, and a table of another kind after a text are all checked;
- the interpreter's own alphabet met each character only now and then in
  random programs, and a wrong 7 passed a thousand of them: one program
  reads all 32 in both cases;
- the generator's texts could lose their dashes, their small letters or
  every read but the first character's, unnoticed: each is counted from
  the source now, with a floor, and the generator's count of its texts is
  held to the source's.

Both lists of survivors, 22 plants, were run again and are caught. Two
needed a second try, and showed the test's own counting wrong: a read "by
a number that is not zero" had been found by a pattern that took a name
beginning with a to f for a hex digit.

Setting floors under rarer things showed what a floor is worth on few
programs. Asked for 100, the test once had a text in 7 of the 54 that ran,
13% where 20,000 programs have 27%. Shares are counted from 300 programs
up, and below that the programs are compared and nothing is counted.
