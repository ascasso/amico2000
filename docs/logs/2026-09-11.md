## Require Small Commits in the Agent Contract

### Summary

The Agent Operating Contract asked for "one or more focused logical commits",
which permitted an agent to land an entire session as one commit and still be
within the letter of the rule. The project owner asked for small commits for
every unit of work, so the bullet was replaced with an explicit definition:
one commit is one unit of work, each commit stands on its own, and its
`CHANGELOG.md` and `docs/logs/` entries travel in the same commit.

### Scope

Guidance only. `AGENTS.md` and `CHANGELOG.md`. No source or behavior changes.

The subject-prefix rule records what the history already does rather than
inventing a new convention: `docs:` (11 commits), `fix:` (5), `ui:` (1) and
`feat(ui):` (1) are the prefixes in use, so those are the ones named, with
Conventional Commits as the general rule for anything new.

The existing `fix:` / `docs:` pairs — such as `43eb9c0` with `816e0b1` for
issue #31 — are explicitly still allowed: a large change may separate the code
from its longer-form documentation. The new rule forbids batching *unrelated*
units, not splitting one unit across a code and a docs commit.

### Verification

`git diff --check` passed. No JavaScript changed, so no `node --check` was
needed; `node --test tests/` was run for the session baseline and passed all
33 tests.

## Pin the Klaus Dormann 6502 Functional Test Fixture (#17)

### Purpose and Scope

`AGENTS.md` has listed "run a known 6502 functional suite, such as Klaus
Dormann's tests" under Pending Verification Work since the CPU core was
written, and Known Limitations #5 says the same. This is the first slice of
that work: pin the fixture and document it. No runner, no test invocation, and
no CPU change — those follow.

### What Was Pinned

Upstream `Klaus2m5/6502_65C02_functional_tests` at revision
`7954e2dbb49c469ea286070bf46cdd71aeb29e4b` (2020-01-05), which carries the
source version string `version 05-jan-2020`. An immutable commit SHA, not a
branch name, so the fixture cannot drift underneath the tests.

Vendored into `tests/fixtures/6502-functional/`:

| File | Bytes | Role |
|---|---|---|
| `6502_functional_test.bin` | 65536 | flat 64KB memory image the runner will execute |
| `6502_functional_test.a65` | 148497 | corresponding assembler source |
| `LICENSE.txt` | 35147 | upstream GPL-3.0 text |
| `manifest.json` | — | local provenance record; not upstream |
| `README.md` | — | attribution, address derivation, coverage limits |

Every downloaded file was verified against its **git blob SHA-1** at that
revision, not merely its size, which proves the bytes are the blobs of the
pinned commit rather than whatever the branch serves today. SHA-256 checksums
are recorded in `manifest.json` for ongoing integrity checking by the runner.

The 728KB assembler listing is deliberately **not** vendored; its bulk buys
nothing at run time. Its URL and SHA-256 are in the manifest so the addresses
below can be re-derived by anyone who fetches it.

### Addresses, and Why They Were Derived Rather Than Assumed

Addresses move between upstream revisions, so each was read out of the listing
at this revision and then cross-checked byte-for-byte against the vendored
image. Agreement between the two is what establishes that the `.bin` and the
`.lst` are the same build:

| Address | Listing | Bytes in the image |
|---|---|---|
| `$0400` entry (`start`) | line 740, `0400 : d8  start cld` | `D8 A2 FF 9A` (`CLD` / `LDX #$FF` / `TXS`) |
| `$3469` success | line 13377, `3469 : 4c6934 > jmp *` | `4C 69 34` |
| `$379D` `nmi_trap` | line 14349 | `4C 9D 37` |
| `$37A3` `res_trap` | line 14350 | `4C A3 37` |
| `$FFFA` vectors | lines 14348-14351 | `9D 37 A3 37 AB 37` |

Assembly-time configuration at this revision: `ROM_vectors = 1`,
`load_data_direct = 1`, `I_flag = 3`, `zero_page = $0A`,
`data_segment = $0200`, `code_segment = $0400`, `disable_selfmod = 0`,
`report = 0`, `disable_decimal = 0`.

### Three Findings That Constrain the Runner

1. **The reset vector is a trap, not the entry point.** With `ROM_vectors = 1`
   the image fills `$FFFA-$FFFF` and points `$FFFC` at `res_trap` (`$37A3`),
   because an unexpected RESET mid-run is an error the suite wants to catch.
   The runner must assign `PC = $0400` directly and must not call
   `CPU6502.reset()`; doing so would land in a failure trap immediately and
   read as a CPU defect that is not there. The upstream source says as much:
   "alter PC to 400 hex (code_segment) and enter a go command".
2. **Every trap is a self-loop, success included.** `$3469` is `JMP $3469` and
   the failure traps are `jmp *`, `bne *`, `bcs *` and friends. So "the PC
   stopped advancing" is only the detection mechanism; the *address* carries
   the entire pass/fail signal. A runner that treats any stopped program as a
   pass would report success for every failing test in the suite, which is
   exactly the hazard the runner checks must rule out.
3. **`report = 0` means no I/O channel is needed.** The suite self-traps rather
   than reporting through a host hook, so it runs against a bare `CPU6502` with
   its plain writable 64KB array — no monitor ROM, no 8255 PIA, no cassette
   callbacks. `disable_selfmod = 0` means parts of the image modify themselves,
   so the whole image must stay writable.

### Licensing

The emulator is MIT; this fixture is GPL-3.0-or-later. They are kept apart
deliberately: the suite is unmodified third-party *test data* in its own
directory, shipped with its own license text and its corresponding source, read
at run time by a test rather than linked into or distributed as part of the
emulator, and no AMICO 2000 source is derived from it. That is mere
aggregation, and it is how emulator projects normally vendor these tests. The
call is recorded in the fixture README so it is visible to anyone reusing the
repository.

### Verification

- All five downloads matched their upstream git blob SHA-1 exactly.
- The three vendored files re-verified against the SHA-256 values written into
  `manifest.json`.
- The image was re-read at `$0400` and `$3469` to confirm `CLD` and a
  jump-to-self at the success address.
- `manifest.json` parses as valid JSON.
- No new dependencies: there is still no `package.json`, and normal test runs
  need no network and no assembler.
- `git diff --check` passed. `node --test tests/` passed all 33 tests both
  before and after, since nothing executable changed.

## Conformance Runner for the Functional Suite (#17)

### Summary

Added `tests/helpers/6502-conformance.js`, which runs the fixture pinned
earlier today against a bare `CPU6502`, and `tests/cpu6502-functional.test.js`,
which invokes it as a normal Node regression check.

**Result: the CPU core passes the suite.** It reaches the success trap at
`$3469` after 30,646,177 instructions and 96,241,367 cycles. That cycle total
matches the figure usually quoted for this suite, which is a further sign the
image ran to completion as intended rather than stopping early somewhere
harmless.

### Approach

The runner instantiates `CPU6502` directly through its existing CommonJS export
and uses its plain writable 64KB array. No `Amico2000`, no monitor ROM, no 8255
PIA, no cassette traps. That isolation is possible because the suite is
assembled with `report = 0`: it signals purely by trapping and needs no I/O
channel, so nothing has to be simulated around it.

Four decisions worth recording:

- **Entry is assigned, not vectored.** `cpu.reset()` is deliberately never
  called, because the image points `$FFFC` at `res_trap` (`$37A3`). Vectoring
  through reset would land in a failure trap and read as a CPU defect that is
  not there. `tests/conformance-runner.test.js` pins this.
- **A pass is an address, not a state.** Every trap in the suite is a loop on
  itself, success included, so "stopped making progress" is only how a trap is
  *detected*. `passed` is set in exactly one branch of the classifier, and only
  from the manifest's success address, so a trap, a halt, an exception, or an
  exhausted budget cannot be mistaken for a pass.
- **The budget counts instructions, not cycles.** A core whose cycle accounting
  is broken is precisely what this suite exists to catch, so it must not be able
  to stall the runner. The budget is 100,000,000 instructions against a measured
  30,646,177 for a full pass — roughly 3x headroom, and about a second of wall
  clock if it is ever exhausted.
- **Cycle totals are reported as diagnostics only.** The suite checks results
  and flags, never timing, so its cycle count is not evidence about cycle
  accuracy. The failure report says so on the line that prints it.

### Cost

About 0.6s for the full suite, including a 16-entry instruction trace kept for
every one of the 30M instructions; the trace costs roughly 200ms of that. Cheap
enough to leave enabled by default and to keep the suite inside the ordinary
`node --test tests/` run rather than behind an opt-in flag.

### Verification

`node --test tests/cpu6502-functional.test.js` passes. Full suite:
`node --test tests/` reports 52 passing, 0 failing. `node --check` passed on
both new files, and `git diff --check` passed.

A negative control was run out-of-tree to confirm the suite is not passing
vacuously: a copy of `cpu6502.js` with the `ADC` overflow flag forced to zero
was rejected at `$062B` after 40,351 instructions, and the instruction trace
showed the `BVC` at `$060E` branching into that trap — the failing check
itself. No repository file was modified by that experiment.

## Verify the Conformance Runner's Failure Reporting (#17)

### Why This Needs Its Own Tests

A passing conformance suite is only worth what its failure path is worth. The
specific hazard here is sharp: because every trap in the suite is a loop on
itself, a runner that concluded "the program stopped, therefore it finished"
would report success for *every* failing test in the suite while looking
perfectly healthy. Nothing in a green run would reveal it.

`tests/conformance-runner.test.js` exists to make that failure mode impossible
to ship unnoticed. It drives the runner with small synthetic programs whose
outcome is known by construction, so the classifier can be tested without the
64KB fixture. This is why `runImage()` is parameterised on image, entry address
and success address rather than hard-coding the real ones.

### What Is Checked

Completion handling:

- a self-loop at the success address is a pass
- the *same* `JMP *` instruction three bytes earlier is a failure — the address
  decides, not the instruction shape

Each way a run can fail, and that it reports as a failure with a usable address:

- a failure trap, with the registers at the trap
- an illegal-opcode halt, reported at the faulting address rather than the byte
  after it, since `CPU6502.step()` has already advanced PC past the opcode when
  it gives up
- an exception thrown by the core, caught rather than escaping
- a multi-instruction loop (`NOP` / `JMP`), which is never a self-loop and so
  can only be stopped by the budget
- the same loop against a stub CPU whose `cycles` never advances, proving the
  budget does not depend on the core's own cycle counter

Then the property all of it rests on, asserted across every outcome the runner
can produce: nothing but reaching the success address is ever marked passed.

Initialisation, diagnostics and the fixture:

- entry at `$0400` with `$FFFC` pointing at a fatal trap, confirming the runner
  does not vector through reset
- the failure report contains PC, opcode, the bytes at PC, registers, decoded
  status flags, instruction and cycle counts, and the cycle line's "diagnostic
  only" qualifier
- the trace ends at the fault, is bounded by its ring buffer, and drops older
  entries
- a missing, malformed, truncated or single-byte-corrupted fixture is rejected
  before anything executes, so a fixture problem cannot be read as an emulator
  defect
- the pinned fixture's manifest still agrees with the bytes it describes

### Two Corrections

Two assertions were wrong on first run, in the test rather than the runner:

- the instruction count at a trap is 5, not 4, because the trap's own `JMP *`
  must execute once before the runner can observe that PC did not move
- `flagsToString(0x24)` is `--U--I--`; the expected literal had `I` in the
  wrong column. The bit order is `N V U B D I Z C`, matching
  `CPU6502.stateToString()`

Both expectations were corrected and the reasoning left in the test as comments.

### Verification

`node --test tests/conformance-runner.test.js` passes all 18. Full suite:
`node --test tests/` reports 52 passing, 0 failing. `node --check` and
`git diff --check` passed.
