# Engineering Log - 2026-11-21

## Let Named Agents Close Issues Without Being Asked

### Purpose and scope

The owner asked for this rule. `AGENTS.md` counted closing an issue as
altering external GitHub state, so an agent needed an explicit request every
time. `#23` was the occasion: an assessment on this date found it fixed by
`1ecbfaf` and already on `master` through PR #40, and could only offer to
close it.

The Agent Operating Contract now carries one exception to that rule: Claude on
an Opus or Fable model, and Codex on an Astra or Sol model, may close an issue
without being asked. The agents and models named are the owner's choice. The
exception covers closing only. Pushing, publishing and every other change to
GitHub state still need an explicit request, and so does closing an issue by
any other agent or model.

The home page build stamp advances to 2026-11-21 with this commit.

### Verification

Text-only change apart from the stamp. `date` reports 2026-11-21 PST, which is
the local date the stamp rule asks for. `git diff --check` and
`node --test tests/` (90) pass.

## Close #23 and Bring the Handoff Notes Up to Date

### Purpose and scope

`#23` reported that a cassette SAVE of the whole `$0000-$FFFF` range wrapped
the 16-bit `.amtape` length field to 0 and reported success. It was closed on
GitHub as completed, under the rule recorded above, with a comment pointing at
`1ecbfaf` and PR #40. No code changed: the fix has been on `develop` since
2026-11-19 and on `master` since PR #40 merged.

`NextSession.md` listed the issue as open work in three places. It now records
`#23` as fixed and closed, lists `#19`, `#20` and `#35` as the open issues, and
drops the "close or reference `#23`" item from Outstanding, which is renumbered
and dated 2026-11-21.

Two other statements in the same status list no longer matched GitHub and are
corrected along the way: `develop` was described as open in a pull request,
but PR #40 merged it on 2026-11-19 local time (05:53 UTC on the 20th); and
`#18` was described as deliberately left open, but it was closed on
2026-09-11.

### Verification

The issue was assessed against the current code before it was closed:

- `tests/cassette-tape-length.test.js` passes. Run against a scratch copy of
  the tree at `1ecbfaf^`, its first check fails because `$0000` reads `$00`
  instead of `$FF`, so the test does exercise the fix.
- A refused SAVE through the `$FBBC` trap, followed by 20,000 monitor
  instructions, leaves the display buffer at `3f 3f 3f 3f 71 71`, which reads
  `0000 FF`, with no tape record stored. The failure is visible at save time,
  which was the issue's complaint.
- Start and end are 16-bit words, so 65,536 bytes is the only length over the
  limit and the guard is complete. `_makeTapeImage()` itself is still
  unguarded, but nothing reachable hands it more than 65,535 bytes: SAVE is
  guarded and an imported tape is bounded by its own 16-bit header.
- Not a `#23` matter, noted for the record: the largest saveable tape,
  `$0000-$FFFE`, imports with `loadTape()` but a LOAD through the `$FC54` trap
  refuses it with `$FF`, because the span covers both PROMs (`#31`).

`gh issue view 23` reports `CLOSED` / `COMPLETED`, and `gh issue list` shows
`#19`, `#20` and `#35` open. Text-only change; `git diff --check` passes.
